# Miku-ZSTD

## 声明

本项目为 MikuMC 服务器原创插件，公开给大众免费使用，MikuMC 服务器与作者 JunXieX 享有项目著作权，本项目非开源项目，请注意。

MikuMC 系列插件交流群：1105054380

在服务端到客户端的下行使用 **Zstandard** 的 Velocity 代理插件，上行保持 Minecraft 原版压缩/解压。在不改动服务端与游戏逻辑的前提下，
把玩家-facing 的出口带宽压到原来的 **1/8 左右**（实测数据见下）。

> ⚠️ **需要客户端安装配套模组**（`miku_zstd`）。这不是单纯的传输优化——它替换的是压缩协议本身，
> 所以必须两端同时使用。未安装模组的客户端**不受任何影响**，走原版 zlib。

---

## 为什么值得用

原版 Minecraft 用 zlib 压缩，且每个包**单独成帧**——帧头、熵表、窗口信息被反复发送。
小包（占真实流量的大多数）压缩后甚至**比原始数据更大**，只能全部直存，白白浪费 CPU 与带宽。

本插件做三件事：

| 优化 | 实测收益 | 说明 |
|---|---|---|
| **一帧多包**（批处理） | **-33.7%** | 一次 flush 之前攒下的包合成一帧再压缩，开销被摊薄，直存帧降到 0 |
| **帧头精简** | **-10.7%** | 去掉 zstd 的 4 字节 magic 与帧头里的 contentSize/dictID（尺寸由协议自带） |
| **滚动历史** | 巨包压到 **14.1%** | 下行两端各自维护 64KB 滑窗当 raw-content 字典，跨帧重复直接命中，**字典本身不传输** |

> 前两行是 5.0.x 的早期基线测量。第三行是 5.0.42 的做法：**训练字典已整体删除**——
> 实机对照显示装上 128KB 训练字典后同一批样本反而多 3.7%，而它唯一可能帮到的小包只占总字节 0.1%。
> 跨帧重复改由滚动历史承担，两端各自对同一条字节流做确定性重建。

### 真实服务器实测

某 Velocity-CTD 生产实例（客户端 mod + 服务端插件）：

```
服务端出站   31.85 MB  →  3.92 MB              省 87.7%
客户端接收   进服突发 15.1 MB/s → 1.8 MB/s     12.2%
             稳态     16.7 KB/s → 10.8 KB/s    64.4%
```

进服阶段（区块与注册表数据）压缩率极高；稳态以小包为主，那里靠的是批处理与滚动历史。

## 安装

### 服务端

1. 把 `Miku-ZSTD-<version>-Velocity.jar` 放入 Velocity 的 `plugins/` 目录
2. 重启代理 —— 首次运行会自动生成 `plugins/Miku-ZSTD/config.yml`
3. 确认日志出现这一行，说明已正常工作：

```
[Zstd] Zstd transport activated (client-ready=true)
```

> **⚠️ `plugins/` 下只能有一个本插件的 jar。** 存在多个同 id 的 jar 时 Velocity 只会加载其中一个，
> 会造成"改了代码却没生效"——这个坑排查起来非常费时。

### 客户端

把 `Miku-ZSTD-<version>-Fabric.jar` 放入 `.minecraft/mods/`。
按 **F8** 可切换统计 HUD，实时显示压缩前后速率与压缩率。

## 工作原理

协议版本 **v11**（Velocity / Paper / Fabric 三端的 `ZstdProtocolVersion.NEGOTIATE` 一致；帧格式 **v7**）。

```
客户端 ──握手(主机名末尾附 \0ZSTD\0 标记)──▶ 服务端
        ◀── zstd:negotiate(只有 [int 协议版本])──
        ── answer([varint 状态]：0=就绪 / 2=保持原版)──▶
        ◀── SetCompression(必须未压缩)──
        ◀── zstd:switch（请求客户端准备下行解码）──
        ── 原版压缩/直存的确认 ──▶
        ═══ 下行启用 zstd 并放行扣包；上行始终保持原版 ═══
```

1. 客户端在握手包主机名末尾附加 `\0ZSTD\0` 标记；服务端嗅探器只认登录连接（`nextState == 2`），
   服务器列表 ping 完全不受影响
2. 服务端在首个出站包前发出 `zstd:negotiate`，**载荷只有协议版本**（4 字节大端）
3. 客户端回一个状态：`0 = 就绪` / `2 = 保持原版`（旧客户端可能仍回 `1 = 需要字典`，
   服务端一律按 `2` 处理）。协议 v8 起**没有 `zstd:dict` 通道**，也不传输任何字典
4. 版本不匹配 / 协商失败 → **双方一致回落原版 zlib**，不会断连
5. 原版发出 `SetCompression`（**必须未压缩**——否则客户端尚未切换就会解析失败）后，
   服务端进入 hold 窗口，扣住后续待发包
6. 服务端安装下行 zstd 编码器与扣包闸门，发送 `zstd:switch`；客户端准备好下行 zstd 解码后，
   经原版上行返回确认。服务端在原版解压器之前识别确认，再释放扣住的包。
   正常上行始终由原版解压器和包解码器处理，服务端不再安装上行 zstd 解码器。

> **为什么训练字典被删掉（v7 → v8）**：它需要采样、训练、下发、CRC 校验、双向装载，
> 而实测收益是负的（多 3.7%），小包覆盖不到 0.1% 的总字节。删掉之后协商只剩一次往返、
> 没有任何字典流量，跨帧重复由滚动历史（协议内自动维护）承担。

### 帧格式（v7）

```
服务端 → 客户端   [varint bodyLen?][varint rawSize][varint dictGen][varint blockCount] + block...   ← 压缩
                 [varint bodyLen?][0][packet]                                                       ← 直存（一帧一包）
客户端 → 服务端   [varint bodyLen][0][packet] 或 [varint bodyLen][dataLength][zlib(packet)]           ← 原版
block              [varint blockRawLen][varint chunkLen][chunk]
压缩帧（rawSize > 0）  解压后 = [varint pktLen][pkt] [varint pktLen][pkt] ...   ← 一个或多个包
```

- **上行（客户端 → 服务端）完全使用原版压缩/解压**：每包按原版阈值压缩或直存，
  不合批、不使用 zstd；切换确认同样经过原版上行。

- **下行仍是 zstd**：`rawSize == 0` 的直存帧，帧体**恰好是一个包**（`[0][packet]`），与原版未压缩帧
  逐字节同形 —— 原版解码器（`CompressionDecoder`）与包解码器都能直接读懂。
  **因此下行直存帧必须一帧一包、且不带任何内层长度前缀、也不带 `dictGen`**：多写一层
  `[varint pktLen]` 时，包解码器读到的"包 id"就是那个长度值 → `Unknown packet` → 玩家进不去服
- **一帧多包仅用于下行**：下行走压缩帧时合批，摊薄帧头与熵表；上行保持原版逐包成帧
- **`dictGen` 是滚动历史字典的代数**（协议 v7 新增）：两端各自维护最近 64KB 原始字节，
  每喂满 256KB 重建一次字典并让代数 +1，**字典本身不传输**；代数对不上即按协议错乱关连接
  （这是一致性校验，不是优化开关）
- **分块**：大帧（>256KB）按字节均分成最多 4 块并行压缩，每块自带原文字节数；
  解压后按序拼回再切包，一个包可以横跨两块
- **magicless zstd 帧**：省 4 字节 magic，且不写 contentSize / dictID
  （解压尺寸由 `rawSize` 提供，字典由两端按同一份滚动历史各自生成，帧内不必也不该带 id）
- **`bodyLen` 只由 Velocity 写**（4.x 管线的压缩编码器把"外层长度 + 压缩"合在同一个处理器里，
  跳过它就必须自带长度）；Paper / Fabric 侧由 prepender 负责——这是刻意设计，缺层或双层都会
  导致对端解码失败
- **服务端仅持有下行压缩上下文**：不再租借上行 zstd 解压上下文
- 小包（<48B，协议层另有 16B 硬地板）压缩后反而膨胀，直接走直存路径

### 协商载荷

| 报文 | 载荷 |
|---|---|
| `zstd:negotiate` | `[int 协议版本]` |
| `answer` | `[varint 状态]` |

> ⚠️ **状态码语义三端必须完全一致**：`0 = 就绪` / `2 = 保持原版`（`1` 已废弃，收到按 2 处理）。
> 服务端严格按 `2` 回落原版 zlib，因此客户端任何返回 `2` 的分支都必须同时放弃激活 zstd——
> 否则会形成「服务端 zlib / 客户端 zstd」的**必断连组合**。

## 配置文件

`plugins/Miku-ZSTD/config.yml`（首次运行生成，**之后不会被覆盖**；删除可重新生成）

> 目录名与插件显示名一致（Velocity 的 plugin id 只允许小写，故取注入路径的父目录再拼 `Miku-ZSTD`）。
> 从旧版本升级时，原有的 `plugins/miku-zstd/`（含 `config.yml`）会在首次启动时自动迁移到
> 新目录，不会丢配置。5.0.42 起训练字典已删除，旧目录里的 `zstd_dicts/` 不再被读写。

```yaml
compression:
  # zstd 压缩等级 (1-22)。
  # 默认 3。实测（按批处理形态）：
  #   小包是收益的主战场，而高等级在这里反而更差——
  #   单包 64B：L3 压到 45.3%，L9 只能压到 57.8%，L3 好 12.5 个百分点；
  #   数据越长高等级才越有优势（8KB 批次上 L9 好约 4 个百分点），
  #   但代价悬殊：L9 的压缩耗时是 L3 的 8~12 倍，而解压耗时与等级无关。
  level: 3

  # 滑动窗口 2^N 字节（20 = 1MB）
  # 实测 window_log 17 / 20 / 23 的压缩率完全相同，但它决定 zstd 哈希表规模
  # （2^(windowLog-1) × 4B，指数增长）且是每连接一份：23 ≈ 16MB，20 ≈ 2MB。
  window_log: 20

  # ── 批处理（压缩帧）──
  # 攒批边界是上游本来就发生的 flush（tick 末尾、区块发送完成、登录期写包），
  # 一次 flush 出一帧，所以合批本身不额外增加延迟。
  # 这个值是【兜底】：只有"上游只 write、始终不 flush"的调用方才轮得到它，
  # 到点强制成帧；正常流量下 flush 一定先到，定时器随即被取消，一次也不触发。
  # 调大它不会攒到更多包，只会把兜底变成常态延迟；0 = 写即成帧（连兜底都不要）。
  batch_window_ms: 50
  batch_max_packets: 64

  # ── 小包跳过压缩（实测阈值，别凭感觉改）──
  # ≤32B 压缩后反而膨胀到 102~113%，48B 起才有收益。
  # 5.0.42 删除训练字典后只剩这一档（原来的 _with_dict 已移除）。
  skip_compress_below_bytes: 48

logging:
  debug: true
```

`logging.debug` 开启时使用本插件的 DEBUG 日志并启用每 60 秒一次的下行帧带宽剖析；关闭时使用 INFO 日志并停止剖析。修改后执行 `/mikuzstd reload` 即时生效。剖析按合批后的原始帧大小分档，不代表单个游戏包的长度分布。
