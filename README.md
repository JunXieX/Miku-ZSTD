# Miku-ZSTD

用 Zstandard 替代 Minecraft 原版 zlib。服务端出站流量可降至原来的约 1/8，且不改动任何游戏逻辑。

需要客户端安装配套模组。

## 为什么值得用

原版 Minecraft 用 zlib 压缩，且每个包单独成帧——帧头、熵表、窗口信息被反复发送。小包（占真实流量的大多数）压缩后甚至比原始数据更大，只能全部直存，白白浪费 CPU 与带宽。

本方案做了四件事：

| 优化 | 实测收益 | 说明 |
|---|---|---|
| 一帧多包（批处理） | **-33.7%** | 时间窗内的多个包合成一帧再压缩，开销被摊薄 |
| 帧头精简 | **-10.7%** | 去掉 zstd 的 4 字节 magic 与帧头里的 contentSize / dictID |
| 字典训练 | 小包 **-23.6%** | 从真实流量采样自动训练，收益集中在小包（正是原版最吃亏的地方） |
| 大帧分块并行 | 降低进服卡顿 | 注册表、区块这类超大帧切成多块并行压缩 |
| **合计** | **-38.3%** | 相对「每包一帧 + 完整帧头」的基线 |

### 真实服务器实测

某 Velocity-CTD 生产实例（客户端模组 + 服务端插件）：

```text
服务端出站   31.85 MB  ->  3.92 MB              省 87.7%
客户端接收   进服突发 15.1 MB/s -> 1.8 MB/s     12.2%
             稳态     16.7 KB/s -> 10.8 KB/s    64.4%
```

进服阶段（区块与注册表数据）压缩率极高；稳态以小包为主，是字典收益的主战场。

## 组件与部署形态

本项目包含三个可部署产物。客户端模组是必需的，服务端按你的架构二选一（或两处都装）。

| 产物 | 部署位置 | 何时需要 |
|---|---|---|
| `Miku-ZSTD-<版本>-Velocity.jar` | Velocity 代理的 `plugins/` | 玩家经 Velocity 代理进服（生产主路径） |
| `Miku-ZSTD-<版本>-Paper.jar` | Paper 服务端的 `plugins/` | 玩家直连、不经过代理的场景 |
| `Miku-ZSTD-<版本>-Fabric.jar` | 客户端 `mods/` | 所有场景都需要 |

典型组合：

- **代理架构**：Velocity 插件 + 客户端模组。带宽优化发生在「代理 ↔ 客户端」这一段
- **直连架构**：Paper 插件 + 客户端模组
- **混合**：Velocity 与 Paper 都装也可以，各自只优化自己那一段

> 三端的版本必须一致。版本不一致时会自动回落原版 zlib（能正常进服，只是没有压缩优化）；若两端一侧生效、另一侧未生效则会断连。

## 运行要求

| | 要求 |
|---|---|
| 代理 | Velocity 4.x |
| 服务端 | Paper 26.2+ / Folia 26.2+ |
| 客户端 | Fabric，Minecraft 26.2+ |
| Java | 25+ |

**Paper / Folia 额外要求**：`server.properties` 的 `network-compression-threshold` 必须 ≥ 0，推荐 256。

本插件是**替换**而非叠加原版压缩，因此不会带来双份 CPU 开销。若该值设为 -1（关闭原版压缩），插件会因缺少切换信号而自动停用并打一条提示——不影响正常进服，只是没有压缩优化。

**Folia**：同一个 jar 直接可用，不需要单独的构建产物或额外配置。

## 安装

### 服务端

1. 把对应的 jar 放入 `plugins/` 目录
2. 重启服务端。首次运行会自动生成配置文件（自带中文注释）：
   - Velocity：`plugins/Miku-ZSTD/config.yml`
   - Paper：`plugins/Miku-ZSTD/config.yml`
3. 确认日志出现这一行，说明已正常工作：

```text
[Zstd] Zstd transport activated (dict=true)          <- Velocity
[Zstd] zstd transport activated on Paper             <- Paper
```

> `plugins/` 下只能有一个本插件的 jar。存在多个同 id 的 jar 时只会加载其中一个，会造成「改了配置却没生效」——这个坑排查起来非常费时。

### 客户端

把 `Miku-ZSTD-<版本>-Fabric.jar` 放入 `.minecraft/mods/`。

进入游戏后按 **F8** 可切换统计 HUD，实时显示上下行的压缩前后速率与压缩率。

首次启动会在游戏目录下生成 `Miku-ZSTD/config.yml`。

## 配置说明

配置文件自带完整中文注释，这里只列最常动的几项。

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `compression.level` | 3 | zstd 压缩等级 1-22。3 已经够用：小包上更高等级反而更差（同一个 64B 包，L3 压到 45.3%，L9 只有 57.8%），而 L9 的 CPU 开销是 8 到 12 倍。只有大包占绝对多数且 CPU 富余时才考虑调到 6 |
| `compression.window_log` | 20 | zstd 窗口大小（2 的幂）。调大能提升大帧压缩率，但每连接内存占用同步上升 |
| `compression.threads` | 0 | 压缩线程数，0 表示自动（核心数减保留值）。混合架构下取「核数减 1」通常最稳 |
| `batch_window_ms` | 2 | 攒包时长。调大能提高压缩率，代价是等量延迟；0 表示立刻成帧 |
| `batch_max_packets` | 64 | 单帧最多合几个包。过大时单帧压缩耗时会变长 |
| `logging.bandwidth_profile` | true | 每 60 秒输出一次带宽剖析，便于判断优化空间在哪 |

> 改动 `level`、`window_log`、`batch_window_ms`、`batch_max_packets` 后需要新连接才生效（已有连接沿用建立时的参数）。

## 常见问题

**Q：进服时提示版本不匹配 / 没有压缩效果？**

三端（Velocity 或 Paper、以及客户端模组）必须是同一版本。版本不一致会自动回落原版 zlib，能进服但没有优化。

**Q：玩家进不去，怎么看是哪一类问题？**

看服务端日志，它明确说明了属于哪一种：

| 日志 | 含义 | 处理 |
|---|---|---|
| `anchors 未出现（compress/decompress 缺失）` | 这条连接没有原版压缩层，插件回落原版。玩家仍能正常进服 | 确认 `network-compression-threshold` ≥ 0 |
| `客户端保持原版 zlib，本端不激活` | 客户端明确拒绝（没装模组或版本不一致） | 安装客户端模组，并与服务端同版本 |
| 有 `zstd transport activated` 但仍掉线 | 协商成功，问题在别处 | 看客户端日志 |

客户端侧若出现 `frame rejected` 或 `illegal inner packet length`，属于帧格式问题，请带上原样日志反馈。

只有一句「连接中断」而没有任何 zstd 相关行，通常是网络层断开，与本插件无关。

**Q：压缩率看起来很差？**

先看 `/mikuzstd status` 里字典是否已训练出来（dictId 非 0）。小包压缩率接近 100% 说明字典还没出来——字典需要一段时间的真实流量才能训练完成。

再看带宽剖析，确认字节主要花在哪个包长区间。

**Q：CPU 占用变高？**

看 `/mikuzstd status` 的压缩线程池一行。若「队列」持续大于 0，说明压缩跟不上流量，此时应降低 `level` 或增加线程，而不是继续调批处理窗口。

**Q：和 Krypton 之类的网络优化模组冲突吗？**

可以共存。两者优化的是不同层面，各自独立生效。

**Q：服务端出问题怎么回滚？**

移除插件 jar 并重启即可。客户端模组可以保留——它在没有服务端配合时会自动按原版工作，不会导致进不去。
